# ADR-0009: Warehouse modeling conventions

- **Status:** Accepted
- **Date:** 2026-10-30
- **Related decisions:** 12 (Warehouse separation), 13 (Idempotency),
  14 (Extensibility)

## Context

Three pipelines will load one `warehouse` schema (ADR-0008). Without shared
conventions, each pipeline would invent its own keys, audit columns and
update rules, and reruns could leave inconsistent data.

## Decision

1. **Naming.** Tables are `warehouse.dim_<entity>` and
   `warehouse.fact_<event>`, in singular snake_case. Every table and column
   has a comment where the meaning is not obvious; each fact table states its
   grain in the table comment.
2. **Dimension keys.** A dimension has a surrogate key `<entity>_key`
   (integer identity, primary key) and its business key `<entity>_id`
   with a `UNIQUE` constraint. Loaders upsert on the business key.
   `dim_date` is the exception: its key is the readable `YYYYMMDD` integer
   `date_key`, identical to `agpp.shared.dates.date_key`.
3. **Facts.** Facts hold foreign keys to dimension surrogate keys and never
   `NULL` keys. A missing or unknown reference points at the dimension's
   "unknown" member (key `-1`), which each dimension defines.
4. **Audit columns.** Every table except `dim_date` has
   `created_at timestamptz NOT NULL DEFAULT now()` and
   `updated_at timestamptz NOT NULL DEFAULT now()`. `updated_at` changes only
   when a row's values change.
5. **History.** Dimensions are Type 1 (overwrite) by default. Type 2 history
   is added only when a business need appears, recorded in its own ADR.
6. **Idempotent loading.** Every load is an upsert on the business key that
   writes a row only if a value differs (`IS DISTINCT FROM`). Loading the
   same input twice leaves the data, including `updated_at`, unchanged.
7. **Time.** Instants are `timestamptz` in UTC. Calendar dates are
   `date` values joined to `dim_date`.
8. `dim_date` is generated by migration with deterministic English names
   (no dependence on database locale) and covers 2000-01-01 to 2049-12-31.

## Alternatives considered

| Option | Why not |
|---|---|
| Natural keys as primary keys everywhere | Wide fact tables, painful key changes, no unknown member. |
| SCD Type 2 everywhere from the start | Heavy, and the sample business rules need no history yet. |
| Truncate-and-reload instead of upserts | Not safe for concurrent readers and loses `created_at`. |
| Generate `dim_date` from Python | The migration is then not a complete description of the database. |

## Consequences

### Positive
- One shape for every dimension and fact; pipelines 2 and 3 copy it.
- Reruns are safe and cheap; unchanged rows are not rewritten.

### Negative / trade-offs
- Type 1 overwrites history; if the business later needs it, that
  dimension needs a migration and a new ADR.
- Surrogate keys add a lookup step in fact loading.

### Follow-ups
- The idempotent upsert helper.
- Product and supplier dimensions with their unknown members arrive with
  the Supplier Product pipeline.
